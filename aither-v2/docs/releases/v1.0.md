# Aither AI Platform — Release v1.0

**Date:** 2026-07-23  
**Version:** 1.0.0  
**Codename:** Production v1.0  

---

## Overview

Aither AI Platform v1.0 is the first production-ready release of the Aither project — an end-to-end AI inference platform built on Kubernetes, featuring a web portal, OpenAI-compatible API, and multi-user support.

---

## New Features

### Portal UI
- **Login/Dashboard** — JWT-based authentication with admin/admin credentials
- **Chat Interface** — Create conversations, send messages, receive AI responses
- **Model Display** — View available models (single model: qwen-32b-base)
- **API Key Management** — Create, list, and revoke API keys from UI
- **Assistant Management** — Create and manage AI assistants linked to models
- **System Status** — Dashboard showing service health and version info

### API
- **OpenAI-Compatible Endpoint** — `/v1/chat/completions` with Bearer token or API Key auth
- **Conversations API** — Full CRUD: create, list, get, delete conversations and messages
- **Models API** — List, create, update, delete registered models
- **API Keys API** — Create, list, revoke keys with SHA256 hashing
- **Assistants API** — Create, update, delete assistants with model binding

### Infrastructure
- **Kubernetes Cluster** — 2-node cluster (n7: worker, n8: control-plane + GPU)
- **vLLM Inference** — qwen-32b-base model via vLLM 32B
- **Nginx Gateway** — Request routing from AI Platform to vLLM
- **In-Cluster Registry** — `10.129.13.78:5000` for container images
- **Persistent Storage** — PVC-backed SQLite for AI Platform and Identity
- **Redis Rate Limiting** — Ready for rate limit enforcement
- **Prometheus Metrics** — Built-in metrics collection across all services

### Operations
- **Health Endpoints** — `/health`, `/ready`, `/version` on all services
- **Structured Logging** — JSON-formatted logs across all Python services
- **Backup Scripts** — Automated SQL dump and restore procedures
- **Gateway `/ready` and `/version`** — Comprehensive healthcheck coverage

## Architecture

```
Browser (User)
    ↓
Portal Frontend (nginx SPA)
    ↓  (proxy /api/*)
Portal Backend (FastAPI BFF)
    ↓  (proxy /api/v1/*)
AI Platform (FastAPI, SQLite)
    ↓  (v1/chat/completions)
Gateway (nginx, single upstream)
    ↓  (v1/completions)
vLLM 32B (qwen-32b-base)
```

### Services

| Service | Technology | Role |
|---------|-----------|------|
| Portal Frontend | nginx + HTML/JS SPA | User interface |
| Portal Backend | Python FastAPI | BFF proxy |
| AI Platform | Python FastAPI | Business logic + SQLite |
| Identity | Python FastAPI | User authentication + JWT |
| Gateway | nginx | Request routing to vLLM |
| vLLM 32B | vLLM | Model inference (qwen-32b-base) |
| Redis | redis:7-alpine | Rate limiting |

## Limitations (Known Issues)

### Functional
1. **Single Model** — Only qwen-32b-base (completion-only, no chat format). qwen-14b-instruct disabled.
2. **No Streaming** — SSE streaming not supported (planned for V1.1)
3. **No Chat Format** — Model is completion-only; `/v1/chat/completions` proxied as completion internally
4. **No Token Refresh** — JWT valid for 24h without rotation

### Infrastructure
5. **K8s API Intermittency** — `dial tcp 10.129.13.78:6443: i/o timeout` from build host
6. **No External DNS** — Services accessible only via ClusterIP within cluster network
7. **No TLS/HTTPS** — All traffic unencrypted (internal cluster only)
8. **Single Replica** — Most services run at 1 replica (Gateway has 2)

### Security
9. **No CSP Headers** — nginx-gateway and portal-frontend lack security headers
10. **No Gateway Rate Limiting** — Redis available but not enforced at Gateway
11. **CORS Set to localhost:3000** — Requires update for production domain

## Architecture Decisions

### AD-01: Single Model (Option B)
- **Decision:** Beta v0.9 / V1.0 supports exactly one model: qwen-32b-base
- **Rationale:** Gateway (nginx-gateway-32b) is single-upstream to vLLM 32B. Multi-model routing would require a new Gateway implementation.
- **Future:** V1.1 restores multi-model with universal LLM Gateway

### AD-02: Portal Backend as BFF
- **Decision:** Portal Backend acts as Backend-For-Frontend, proxying API requests to AI Platform
- **Rationale:** Decouples frontend from backend services; single auth point
- **Implementation:** nginx `location /api/` → `aither-portal-backend:8000` → `aither-ai-platform:8000`

### AD-03: SQLite with PVC
- **Decision:** AI Platform and Identity use SQLite on PersistentVolumeClaims
- **Rationale:** Simple, zero-configuration, adequate for pilot scale
- **Trade-off:** Not horizontally scalable; for V1.1 consider PostgreSQL migration

### AD-04: Single vLLM API Key
- **Decision:** All Gateway-to-vLLM requests use one `VLLM_API_KEY` from K8s Secret
- **Rationale:** Single upstream simplifies Gateway configuration

## Installation

```bash
# Prerequisites
- Kubernetes cluster (2+ nodes, one GPU)
- kubectl configured
- In-cluster Docker registry

# Deploy
kubectl apply -f manifests/mvp-roadmap/

# Verify
kubectl get pods -n aither-inference
# Expected: 11/11 pods Running
```

## Upgrading

```bash
# 1. Build new image
docker build -t 10.129.13.78:5000/aither-ai-platform:v1.0.1 -f Dockerfile .

# 2. Push to registry
docker push 10.129.13.78:5000/aither-ai-platform:v1.0.1

# 3. Update deployment
kubectl set image deployment/aither-ai-platform \
  ai-platform=10.129.13.78:5000/aither-ai-platform:v1.0.1 \
  -n aither-inference
```
