# CB-WEBUI-01 — Жизненный цикл API-ключей

## Текущее состояние

API-ключи управляются через BFF (Backend-for-Frontend) по эндпоинту `/api/v1/tokens`. Система находится в состоянии **частичной готовности**.

## Статус реализации

| Функция | Эндпоинт | Статус | Примечание |
|---------|----------|--------|------------|
| Просмотр списка ключей | `GET /api/v1/tokens` | ⚠️ Частично | Может не загружаться при проблемах с BFF |
| Создание ключа | `POST /api/v1/tokens` | ✅ Реализован | Поддерживает выбор моделей и scopes |
| Отзыв ключа | `DELETE /api/v1/tokens/{id}` | ✅ Реализован | С подтверждением через `confirm()` |
| Валидация ключа | Через BFF middleware | ✅ Реализован | BFF проверяет токен при запросах |

## Безопасность token_id

### Что такое token_id?

`token_id` — это 12-символьный hex-идентификатор, генерируемый через `secrets.token_hex(6)`. Он используется **исключительно** как первичный ключ в базе данных для ссылок на токены.

### Почему token_id безопасен?

| Свойство | Значение |
|----------|----------|
| **Генерация** | `secrets.token_hex(6)` — криптографически безопасный генератор |
| **Длина** | 12 hex-символов (48 бит как идентификатор) |
| **Назначение** | Только идентификация записи в БД (первичный ключ) |
| **Не является секретом** | Не участвует в аутентификации, не передаётся как Bearer-токен |
| **Не используется в подписи** | Не участвует в JWT, хешировании или шифровании |
| **Видимость** | Может появляться в URL (`/api/v1/tokens/{token_id}`), логах, UI |

### Что НЕ является token_id?

❌ `token_id` ≠ аутентификационный токен
❌ `token_id` ≠ Bearer-токен
❌ `token_id` ≠ сессионный ключ

### Что используется для аутентификации?

Поле `token` — это реальный аутентификационный токен формата `athr_<urlsafe_base64>`:
- Генерируется через `secrets.token_urlsafe(32)` (~256 бит энтропии)
- Хешируется bcrypt/scrypt перед сохранением в БД
- Возвращается пользователю **один раз** при создании
- Передаётся в заголовке `Authorization: Bearer athr_...`

### Код генерации

```python
import hashlib
import secrets

def generate_key():
    """BFF key generation logic."""
    raw = secrets.token_urlsafe(32)
    token = f"athr_{raw}"                           # Аутентификационный токен
    token_hash = hashlib.sha256(token.encode()).hexdigest()  # Хеш для БД
    prefix = token[:12]                              # Префикс для UI
    token_id = secrets.token_hex(6)                  # 12 hex: идентификатор БД
    return {
        "token": token,           # СЕКРЕТ — возвращается один раз
        "hash": token_hash,       # Сохраняется в БД
        "prefix": prefix,         # Для UI-отображения
        "token_id": token_id      # Первичный ключ БД
    }
```

## Scope-модель (грани прав доступа)

| Scope | Модель | Тип доступа |
|-------|--------|-------------|
| `model:14b:chat` | qwen-14b | Чат (диалоговый режим) |
| `model:32b:chat-adapter` | qwen-32b-base | Чат-адаптер (диалоговый) |
| `model:32b:completion` | qwen-32b-base | Completion (продолжение текста) |

## Интерфейс создания ключа

### Поля формы:

| Поле | Тип | Описание |
|------|-----|----------|
| Название ключа | `text` | Произвольное имя (например, «Разработка») |
| Модели | `select` | «Обе модели», «Только qwen-14b», «Только qwen-32b-base» |

### Логика выбора scope:

```javascript
let scopes = [];
if (models === 'both' || models === 'qwen-14b') {
    scopes.push('model:14b:chat');
}
if (models === 'both' || models === 'qwen-32b-base') {
    scopes.push('model:32b:chat-adapter', 'model:32b:completion');
}
```

### Процесс создания:

1. Пользователь заполняет форму и нажимает «Создать»
2. Отправляется `POST /api/v1/tokens` с `{name, scopes}`
3. BFF генерирует токен и `token_id`, возвращает полный токен **один раз**
4. Интерфейс показывает ключ с предупреждением: «⚠️ Сохраните ключ сейчас — он больше не будет показан!»
5. Ключ можно скопировать кнопкой «Копировать»

## Отзыв ключа

1. На странице «🔑 API Ключи» отображается таблица ключей
2. Для каждого активного ключа доступна кнопка «Отозвать»
3. При нажатии — диалог подтверждения: «Отозвать этот ключ? Это действие нельзя отменить.»
4. После подтверждения — `DELETE /api/v1/tokens/{token_id}` (используется `token_id`, не полный токен)
5. Список ключей обновляется

## Известные проблемы

### Страница API-ключей не загружается

**Симптом:** При переходе на страницу «🔑 API Ключи» отображается «Не удалось загрузить ключи.»

**Вероятная причина:** BFF не реализует endpoint `/api/v1/tokens` полностью или возвращает ошибку.

**Обходной путь:** Прямое использование API через curl:

```bash
# Создание ключа
curl -X POST https://fb1.spb.ru:443/api/v1/tokens \
  -H "Content-Type: application/json" \
  -H "Cookie: session=..." \
  -d '{"name": "test", "scopes": ["model:14b:chat"]}'

# Просмотр ключей
curl https://fb1.spb.ru:443/api/v1/tokens \
  -H "Cookie: session=..."

# Отзыв ключа (по token_id)
curl -X DELETE https://fb1.spb.ru:443/api/v1/tokens/{token_id} \
  -H "Cookie: session=..."
```

## Закрытие инцидента INC-2026-TRACK-A-PRIVATE-KEY

**Инцидент:** Утечка приватного ключа делегирования RSA-2048 в Git-репозиторий.

**Статус:** ✅ **CLOSED (Remediated)** — 2026-07-25

**Влияние на систему API-ключей:**
- Инцидент НЕ затрагивал агентские API-ключи (токены формата `athr_*`)
- Скомпрометированный ключ использовался для подписи JWT-токенов делегирования (RS256), а не для API-аутентификации
- API-ключи (`athr_*`) всегда генерировались и управлялись отдельно через BFF `/api/v1/tokens`
- Процедуры безопасного хранения токенов (хеширование + префикс) не пострадали

**Извлечённые уроки, применённые к системе API-ключей:**

| Мера | Применение к API-ключам |
|------|--------------------------|
| `*.pem` в `.gitignore` | Политика распространена на все секреты |
| Pre-commit hook: Gitleaks | Обнаруживает токены формата `athr_*` при попытке коммита |
| CI: TruffleHog | Полное сканирование истории на все типы секретов |
| Хранение секретов только в K8s Secrets | BFF хранит хеши токенов в БД, а не raw-ключи |
| Никаких секретов в файлах репозитория | Все ключи и токены — через переменные окружения/Secrets |
