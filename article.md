# Развёртывание мультимодельной LLM-платформы Aither на K8s с GPU

> **Дата:** 05.07.2026  
> **Автор:** Сергей Кравчук, Группа разработки AI-систем, АО «Гринатом»  
> **Версия:** 1.0 (MVP)

---

## 1. Аннотация

В рамках пилотного проекта УВиОС развёрнута инфраструктура для инференса больших языковых моделей (LLM) на базе Kubernetes с GPU-ускорением. Платформа Aither обеспечивает:

- **Высокопроизводительный инференс** через vLLM (tensor parallelism, PagedAttention)
- **Маршрутизацию запросов** через собственный Gateway с выбором модели
- **Веб-интерфейс** для тестирования и демонстрации (чат с переключением моделей)
- **Горизонтальную масштабируемость** за счёт архитектуры на базе K8s

Платформа развёрнута на изолированном контуре (VPN, закрытый сегмент) с перспективой расширения до промышленного кластера.

### 2.1. Узлы

| Узел | IP | Роль | ОС |
|---|---|---|---|

### 2.2. Сетевая связность

```
Интернет (Telegram) ←→ VPS1 ←—WireGuard—→ VPS2 ←—SSH-туннель—→ 40.51 (K8s)
```

- **WireGuard VPN** между VPS1 и VPS2: стабильный канал 200–400 KB/s
- **VPS2 → 40.51**: прямой SSH-доступ (без VPN, локальная сеть тестовой зоны)
- **40.51**: изолирован от интернета, весь трафик через VPS2

### 2.3. Компоненты платформы

| Компонент | Технология | Назначение |
|---|---|---|
| **Hermes Agent** | Python (Nous Research) | Telegram-бот, точка входа пользователей |
| **Gateway** | FastAPI, порт 30900 | Маршрутизация: выбор модели, проксирование к vLLM |
| **vLLM** | v0.24.0, PyTorch | Высокопроизводительный LLM-инференс |
| **PostgreSQL** | 15+ | Хранение метаданных (пользователи, токены, сессии) |
| **Redis** | 7+ | Кэш сессий, очередь запросов |
| **Aither Portal** | HTML/JS (SPA) | Веб-интерфейс: чат с выбором модели |

### 2.4. Поток запроса

1. Пользователь → Telegram → Hermes Agent (VPS1)
2. Hermes → Gateway (localhost:30900): выбор модели, параметры
3. Gateway → VPS2 (SSH-туннель) → K8s Service `vllm-qwen:8000`
4. vLLM → GPU (tensor parallelism: 2× Quadro RTX 6000)
5. Ответ возвращается по обратному пути

### 3.2. Ограничения текущего оборудования

| Ограничение | Влияние | Решение |
|---|---|---|
| **Нет NVLink** | Tensor Parallelism работает через PCIe (медленнее) | NVLink-мост между GPU |
| **Turing SM 7.5** | Flash Attention 2 недоступен (требует SM 8.0+) | `--enforce-eager` (PagedAttention без FA2) |
| **24 GB VRAM** | FP16-модели >12B параметров не влезают на 1 GPU | TP=2 (две GPU) или INT4-квантизация |
| **1 GPU-узел** | Нет отказоустойчивости | Добавление 2-го и 3-го узлов |
| **Медленный VPN** | Загрузка моделей часами | Прямой интернет на 40.51 |

| **FastAPI** | 0.115+ | Gateway |

### 4.2. Конфигурация vLLM (рабочий конфиг)

```bash
--model /models/Qwen2.5-14B-Instruct \
--dtype half \                        # FP16
--max-model-len 4096 \                 # Контекстное окно
--gpu-memory-utilization 0.90 \        # 90% VRAM под KV-кэш
--tensor-parallel-size 2 \             # Обе GPU (28 GB → 2×14 GB)
--enforce-eager                        # Без Flash Attention 2 (Turing)
```

### 4.3. Конфигурация containerd для GPU

```toml
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.nvidia]
  runtime_type = "io.containerd.runc.v2"
  [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.nvidia.options]
    BinaryName = "/usr/local/nvidia/toolkit/nvidia-container-runtime"
    SystemdCgroup = true
```

**Режим:** `csv` (legacy) — CDI отключён из-за бага с `unresolvable CDI devices`.

## 6. Выявленные проблемы и решения

### 6.1. Flash Attention 2 несовместим с Turing (SM 7.5)

**Симптом:** `FA2 is only supported on devices with compute capability >= 8`

**Причина:** Quadro RTX 6000 — архитектура Turing (SM 7.5), FA2 требует Ampere (SM 8.0+).

**Решение:** `--enforce-eager` — отключает FA2, использует стандартный attention (PagedAttention без fused-ядер). Потери производительности: ~15–20%.

### 6.2. VLLM_PORT автоинжект K8s

**Симптом:** `ValueError: VLLM_PORT appears to be a URI 'tcp://10.102.127.135:8000'`

**Причина:** K8s Service с именем `vllm-qwen` инжектит переменную окружения `VLLM_QWEN_PORT_8000_TCP=tcp://...`. vLLM 0.24 парсит ВСЕ переменные с префиксом `VLLM_` и падает.

**Решение:** Явно задать `VLLM_PORT=8000` в env деплоймента (перебивает автоинжект).

### 6.3. Невозможность запустить Qwen 14B на 1 GPU (24 GB)

**Симптом:** `torch.OutOfMemoryError: 21.97 GiB занято, ещё требуется 270 MiB`

**Причина:** Веса модели FP16 занимают 28 GB — больше 24 GB одной GPU.

**Решение:** `--tensor-parallel-size 2` — модель распределяется на обе GPU (по ~14 GB на каждую).

### 6.4. vLLM 0.24: архитектурная инспекция Qwen2 падает в сабпроцессе

**Симптом:** `pynvml.nvmlDeviceGetHandleByIndex` — сабпроцесс не видит GPU

**Причина:** Баг в vLLM 0.24 — при инспекции архитектуры Qwen2 запускается сабпроцесс `python3 -m vllm.model_executor.models.registry`, который не наследует GPU-доступ от K8s device plugin (CDI/CSV context).

**Решение:** Переход на `:latest` (0.24) с `--trust-remote-code` не помог. Баг обходится правильной настройкой рантайма (csv-режим вместо CDI) + `--enforce-eager`.

### 6.5. CDI device resolution failure

**Симптом:** `failed to inject CDI devices: unresolvable CDI devices nvidia.com/gpu=GPU-...`

**Причина:** Device Plugin генерирует CDI-спеки в `/var/run/cdi`, но containerd в режиме `auto` пытается их применить и не может разрешить (баг GPU Operator + containerd).

**Решение:** Переключение `nvidia-container-runtime` в режим `csv` (legacy):
```toml
[nvidia-container-runtime]
mode = "csv"   # вместо "auto"
```

### 6.6. Повреждение файлов модели при медленном SCP

**Симптом:** `SafetensorError: incomplete metadata`, `config.json` из нулевых байтов

**Причина:** SCP через VPN (200 KB/s) прерывается, оставляя недокачанные файлы.

**Решение:** 
- Контрольная сумма после копирования (`ls -lh` + проверка размера)
- При сбое — повторное копирование только повреждённого шарда
- **План:** прямой интернет на 40.51 (заявка подана)

## 8. Необходимость NVLink

**Ключевое ограничение текущей конфигурации** — отсутствие NVLink. При работе в режиме Tensor Parallelism (TP=2) обмен градиентами и активациями между GPU идёт через PCIe:

| Параметр | PCIe 3.0 x16 | NVLink 2.0 (Quadro RTX) |
|---|---|---|
| **Пропускная способность** | ~16 GB/s | ~50 GB/s (на мост) |
| **Задержка** | Высокая (DMA) | Низкая (прямой доступ) |
| **All-reduce (TP=2)** | 30–50% накладных расходов | 5–10% накладных расходов |

**С NVLink:**
- Ускорение TP в 1.5–2×
- Возможность эффективного TP=4 на 4× Quadro RTX 6000 → модели до 56B параметров (FP16)
- Перспектива NVSwitch для 8+ GPU → модели 70B+

**NVLink-мост для Quadro RTX 6000:** NVIDIA NVLink Bridge (2-slot, 3-slot) — ~$80–120 за штуку.

## 9. Заключение

Платформа Aither успешно развёрнута в MVP-конфигурации: одна модель (Qwen 14B) обслуживает запросы через Telegram-бота и веб-интерфейс. Выявлен и задокументирован ряд технических проблем, характерных для эксплуатации GPU в изолированных средах.

**Ключевые выводы:**
1. vLLM — зрелое решение для production-инференса, но требует точной настройки под оборудование
2. Turing-архитектура (Quadro RTX) имеет ограничения, обходимые флагами запуска
3. Отсутствие NVLink — узкое место для многомодельных/многопользовательских сценариев
4. Изолированный контур (без интернета) кратно замедляет развёртывание и обновление

**Следующий шаг:** получение прямого интернета на GPU-узел, ремонт второго хоста, установка NVLink-мостов.
