# 05-EXTERNAL-AUDIT

**Проект:** Aither / AI Hermes MVP

**Этап:** Stage 10 — MVP Final Acceptance / RC1 Gate

**Версия:** 1.0 RC1

**Статус:** Нормативный документ

---

# 1. Назначение

Настоящий документ устанавливает порядок независимого внешнего аудита результатов Stage 10 и правила присвоения итоговых статусов.

---

# 2. Цель внешнего аудита

Цель аудита — независимо подтвердить, что:

- требования Stage 10 выполнены;
- опубликованные изменения соответствуют заданию;
- доказательная база достаточна;
- критические дефекты отсутствуют либо устранены;
- репозиторий находится в согласованном состоянии;
- контрольная точка RC1 может быть пройдена.

---

# 3. Полномочия внешнего аудитора

Внешний аудитор ChatGPT уполномочен:

- проверять Commit SHA;
- анализировать diff и список изменённых файлов;
- проверять содержимое документов, кода и конфигураций;
- проверять Evidence;
- выявлять замечания;
- классифицировать замечания;
- требовать корректирующие действия;
- присваивать статусы аудита;
- принимать или отклонять результат Stage 10.

Только внешний аудитор может присваивать статусы:

- `PASSED`;
- `PASS WITH FINDINGS`;
- `FAILED`;
- `CONNECTOR VERIFIED`.

---

# 4. Независимость проверки

Отчёт Hermes не является окончательным подтверждением результата.

Внешний аудитор обязан самостоятельно проверить предоставленный Commit SHA и связанные материалы через доступный доверенный механизм.

Для GitHub-репозитория основным методом проверки является GitHub Connector.

Обычный веб-поиск не заменяет проверку Commit SHA через GitHub Connector.

---

# 5. Входные данные аудита

Для начала проверки Owner или Hermes предоставляет:

1. полный или сокращённый Commit SHA;
2. имя ветки;
3. перечень изменённых файлов;
4. краткий отчёт о выполнении;
5. результаты локальных проверок;
6. ссылки на Evidence;
7. перечень известных ограничений;
8. Parent commit или базовый Commit SHA, если это требуется для проверки последовательности изменений.

При отсутствии Commit SHA публикация не считается переданной на аудит.

---

# 6. Обязательная процедура проверки

Внешний аудитор выполняет:

1. идентификацию репозитория;
2. получение коммита через GitHub Connector;
3. подтверждение полного Commit SHA;
4. проверку сообщения коммита;
5. проверку автора и даты;
6. проверку Parent commit, если он заявлен;
7. анализ списка изменённых файлов;
8. анализ diff/patch;
9. сопоставление изменений с заданием;
10. проверку отсутствия несанкционированных изменений;
11. анализ Evidence;
12. классификацию найденных замечаний;
13. принятие итогового решения.

---

# 7. Проверка границ изменений

Аудитор должен определить:

- изменены ли только разрешённые файлы;
- отсутствуют ли изменения runtime-компонентов при документационной публикации;
- отсутствуют ли удалённые или переименованные файлы без разрешения;
- не изменён ли смысл утверждённых требований;
- не добавлены ли несанкционированные функции;
- соответствует ли структура репозитория заданию.

Выход за согласованные границы изменений является замечанием и может привести к статусу `FAILED`.

---

# 8. Классификация замечаний

Замечания классифицируются следующим образом.

## 8.1 Critical

Критическое замечание:

- делает результат непригодным;
- нарушает безопасность;
- нарушает целостность данных;
- скрывает фактический провал проверки;
- препятствует воспроизведению;
- нарушает обязательное требование RC1;
- содержит несанкционированные изменения.

Наличие открытого Critical finding означает `FAILED`.

## 8.2 Major

Существенное замечание:

- затрагивает обязательную функцию;
- делает Evidence недостаточным;
- создаёт значимый риск эксплуатации;
- требует исправления до окончательной приёмки.

Открытое Major finding обычно означает `FAILED` или `PASS WITH FINDINGS` только при явно обоснованном исключении.

## 8.3 Minor

Некритическое замечание:

- не влияет на основную работоспособность;
- связано с оформлением, ясностью или неполной документацией;
- может быть устранено после RC1 без существенного риска.

Допускается статус `PASS WITH FINDINGS`.

## 8.4 Observation

Наблюдение или рекомендация, не являющаяся несоответствием.

---

# 9. Итоговые статусы

## 9.1 CONNECTOR VERIFIED

Присваивается, если:

- Commit SHA существует;
- коммит получен через GitHub Connector;
- подтверждены его метаданные;
- проверены список файлов и diff.

Этот статус подтверждает факт и содержание публикации, но сам по себе не означает полного прохождения RC1.

## 9.2 PASSED

Присваивается, если:

- все обязательные требования выполнены;
- Evidence достаточен;
- Critical и Major findings отсутствуют;
- изменения соответствуют заданию;
- обязательные проверки завершены успешно.

## 9.3 PASS WITH FINDINGS

Присваивается, если:

- обязательные требования в основном выполнены;
- имеются только допустимые некритические замечания;
- замечания задокументированы;
- определены владельцы и сроки устранения.

## 9.4 FAILED

Присваивается, если:

- существует Critical finding;
- обязательное требование не выполнено;
- Evidence отсутствует или недостоверен;
- изменения не соответствуют заданию;
- коммит не может быть независимо подтверждён;
- выявлены несанкционированные изменения.

## 9.5 PENDING EXTERNAL VERIFICATION

Используется как промежуточное состояние, если независимая проверка ещё не завершена или GitHub Connector временно недоступен.

Этот статус не является приёмкой.

---

# 10. Повторный аудит

Повторный аудит обязателен, если:

- опубликован исправляющий коммит;
- изменён ранее проверенный Evidence;
- устранены Major или Critical findings;
- изменены обязательные документы Stage 10;
- обнаружено расхождение между отчётом Hermes и репозиторием.

Повторная проверка выполняется по новому Commit SHA.

---

# 11. Формат решения аудитора

Итоговое решение должно содержать:

- репозиторий;
- ветку;
- полный Commit SHA;
- проверенные файлы;
- метод проверки;
- перечень findings;
- итоговый статус;
- заключение о возможности продолжения или закрытия стадии.

---

# 12. Запреты

Внешний аудитор не должен:

- присваивать `CONNECTOR VERIFIED` без проверки через GitHub Connector;
- принимать отчёт Hermes как единственное доказательство;
- игнорировать изменения вне согласованного scope;
- скрывать обнаруженные критические замечания;
- подтверждать этап при недостаточном Evidence.

Hermes не должен:

- объявлять собственный результат принятым;
- присваивать `PASSED` или `CONNECTOR VERIFIED`;
- изменять Evidence после передачи на аудит без нового коммита;
- скрывать ошибки, неуспешные тесты или ограничения.

---

# 13. Условие прохождения RC1

Контрольная точка RC1 может считаться пройденной только после:

1. публикации полного комплекта Stage 10;
2. подтверждения необходимых Commit SHA;
3. проверки Evidence;
4. закрытия обязательных findings;
5. присвоения внешним аудитором статусов `CONNECTOR VERIFIED` и `PASSED`;
6. оформления итогового решения о закрытии Stage 10.
