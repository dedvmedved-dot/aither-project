# 04-EVIDENCE-STANDARD

**Проект:** Aither / AI Hermes MVP

**Этап:** Stage 10 — MVP Final Acceptance / RC1 Gate

**Версия:** 1.0 RC1

**Статус:** Нормативный документ

---

# 1. Назначение

Настоящий документ устанавливает обязательные требования к доказательной базе (Evidence), предоставляемой для независимой проверки результатов Stage 10.

Evidence является основанием для принятия решения о прохождении контрольной точки RC1.

---

# 2. Общие принципы

Доказательная база должна быть:

- проверяемой;
- воспроизводимой;
- относимой к конкретному требованию;
- актуальной на момент аудита;
- непротиворечивой;
- достаточной для независимого подтверждения результата;
- размещённой в согласованном репозитории либо в явно указанном доверенном источнике.

Утверждения без подтверждающих материалов не считаются Evidence.

---

# 3. Обязательная структура Evidence

Для каждого проверяемого требования должны быть указаны:

1. идентификатор требования;
2. краткое описание проверяемого результата;
3. способ проверки;
4. команда, сценарий или последовательность действий;
5. ожидаемый результат;
6. фактический результат;
7. ссылка на файл, лог, отчёт, артефакт или Commit SHA;
8. дата и время получения результата;
9. сведения об окружении;
10. итоговый статус проверки.

---

# 4. Допустимые виды Evidence

К допустимым видам Evidence относятся:

- исходный код;
- конфигурационные файлы;
- автоматизированные тесты;
- результаты тестов;
- журналы выполнения;
- отчёты CI/CD;
- Commit SHA и diff;
- снимки состояния системы;
- машинно-читаемые отчёты;
- инструкции по воспроизведению;
- контрольные суммы артефактов;
- подтверждённые результаты проверки через GitHub Connector.

Снимок экрана без команды, контекста и воспроизводимой процедуры не является достаточным Evidence, если существует более надёжный способ проверки.

---

# 5. Требования к логам

Логи должны:

- содержать дату и время;
- однозначно указывать проверяемый компонент;
- включать выполненную команду или идентификатор теста;
- содержать полный результат без скрытия существенных ошибок;
- не содержать секреты, токены, пароли и персональные данные;
- сохраняться в текстовом или машинно-читаемом формате;
- иметь стабильный путь в репозитории либо ссылку на доверенный источник.

Запрещается вручную редактировать фактические результаты выполнения так, чтобы изменялся смысл Evidence.

---

# 6. Требования к воспроизводимости

Для повторной проверки должны быть указаны:

- версия программного обеспечения;
- версия образов и зависимостей;
- параметры запуска;
- переменные окружения без раскрытия секретов;
- используемые конфигурации;
- предварительные условия;
- последовательность команд;
- критерии успешного завершения.

Если проверка зависит от внешнего сервиса, это должно быть явно отмечено.

---

# 7. Связь Evidence с требованиями

Каждый Evidence должен ссылаться минимум на одно конкретное требование Stage 10.

Одно доказательство может подтверждать несколько требований только при наличии явного обоснования.

Не допускаются:

- Evidence без идентификатора требования;
- ссылки на несуществующие файлы;
- ссылки на локальные пути, недоступные внешнему аудитору;
- неполные выдержки, скрывающие итог проверки;
- результаты, полученные на неизвестной версии системы.

---

# 8. Классификация результатов

Для каждого элемента Evidence устанавливается один из статусов:

- `PASS` — требование подтверждено;
- `PASS WITH FINDINGS` — требование подтверждено, имеются некритические замечания;
- `FAIL` — требование не подтверждено;
- `NOT TESTED` — проверка не выполнена;
- `NOT APPLICABLE` — требование неприменимо с обоснованием;
- `BLOCKED` — проверка заблокирована внешней зависимостью или критическим дефектом.

Статус `NOT APPLICABLE` без письменного обоснования считается `NOT TESTED`.

---

# 9. Хранение и именование

Рекомендуемая структура:

```text
docs/stage10/evidence/
├── README.md
├── requirements-matrix.md
├── logs/
├── reports/
├── checks/
└── artifacts/
```

Имена файлов должны быть понятными, устойчивыми и отражать назначение материала.

Рекомендуемый формат:

```text
<requirement-id>-<check-name>-<date>.<extension>
```

---

# 10. Контроль целостности

Для значимых файлов и итоговых артефактов должны быть указаны:

- Commit SHA;
- путь в репозитории;
- при необходимости — контрольная сумма SHA-256;
- версия или тег;
- дата формирования.

Evidence, изменённый после завершения аудита, подлежит повторной проверке.

---

# 11. Ответственность Hermes + DeepSeek

Hermes + DeepSeek обязаны:

1. собрать Evidence;
2. проверить его полноту;
3. исключить секреты и чувствительные данные;
4. обеспечить воспроизводимость;
5. связать Evidence с требованиями;
6. выполнить commit и push;
7. предоставить Commit SHA;
8. сообщить обо всех известных ограничениях и неуспешных проверках.

Hermes не имеет права самостоятельно присваивать итоговые статусы `PASSED` и `CONNECTOR VERIFIED`.

---

# 12. Критерии приемлемости Evidence

Evidence принимается внешним аудитором, если:

- источник доступен;
- содержимое относится к проверяемому требованию;
- результат воспроизводим либо независимо подтверждаем;
- отсутствуют противоречия;
- соблюдена целостность;
- нет скрытых критических ошибок;
- предоставлен Commit SHA или эквивалентный идентификатор версии.

Недостаточная доказательная база является основанием для замечания или отказа в приёмке требования.

---

# 13. Итоговое положение

Наличие документа, отчёта или заявления само по себе не подтверждает выполнение требования.

Требование считается подтверждённым только после независимой проверки предоставленного Evidence внешним аудитором.
