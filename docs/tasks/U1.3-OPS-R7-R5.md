## 10.1. Главный принцип

```text
TRUTH OVER PASS
```

Честный `BLOCKED` является допустимым результатом.

Ложный `DONE` является нарушением задания.


## 10.3. Немедленное обновление

После каждого действия Hermes обязан локально обновить checklist:

* код написан;
* commit создан;
* deployment выполнен;
* test запущен;
* test завершён;
* evidence создан;
* defect обнаружен;
* blocker возник;
* Owner action выполнен.

Committed checkpoint checklist обязателен после каждого direction implementation commit и evidence commit.

## 10.4. Одно основное направление за раз

Hermes обязан назначать:

```text
CURRENT PRIMARY DIRECTION
```

Новое основное направление запрещено начинать, пока текущее не достигло:

```text

FAILED
BLOCKED
```

Допускается параллельно ожидать только Owner action по Direction 15.

Техническая зависимость между направлениями должна быть записана:

```text

Direction X blocks Direction Y
```

## 10.5. Не выполнять работу по памяти

Перед каждым commit Hermes обязан перечитать:


```text

```

## 10.6. Двухшаговый direction commit pattern

Требование Hermes «не создавать итоговый commit до evidence» уточняется технически.

Для каждого направления используется:

```text

→ deploy exact commit
```

Implementation commit не означает `DONE`.

Commit message запрещено называть:

```text

accepted

```

до committed evidence и статуса `DONE`.

# 16. Direction 19 — User lifecycle administration

Создать безопасный административный CLI:

```text
scripts/admin/manage_users.py
```

Команды:

```text
list
inspect
disable
enable
block
unblock
reset-password
invalidate-sessions
delete
```

Требования:

1. Не выводить password hash.
2. Не выводить raw session.
3. Не выводить API key.
4. Использовать user ID или exact normalized username.
5. Все изменения журналировать безопасно.
6. Password reset использовать Argon2id.
7. Temporary password выводить один раз либо принимать через secure stdin.
8. Reset инвалидирует старые sessions.
9. Disable/block немедленно прекращает доступ.
10. Delete выполняется как controlled soft delete.
11. User API keys отзываются при delete.
12. Invite history сохраняется без plaintext.

Tests:

* disable active user;
* old session rejected;
* login rejected;
* enable restores login;
* password reset;
* old password rejected;
* new password succeeds;
* session invalidation;
* soft deletion;
* deleted user cannot re-register без policy decision;
* foreign-user modification denied техническому пользователю без admin permission.
