# 1. Создание invite-кодов

В рамках R7-R4 необходимо реализовать **безопасный административный CLI** для создания и управления invite-кодами.

Защищённый HTTP endpoint в R7-R4 не требуется.

Предварительное ручное добавление invite-кодов непосредственно командами Redis не считается законченной реализацией и запрещено как штатный механизм.

Обязательный путь:

`scripts/admin/manage_registration_invites.py`

Минимальные команды CLI:

```text
create
list
inspect
revoke
```

Команда `create` должна поддерживать:

```text
--expires-in
--model-scope
--description
```

Допускается создание нескольких model scopes, если это соответствует принятой RBAC-модели.

CLI обязан:

1. Проверять административное право на выполнение через локальную операционную модель сервера.
2. Работать только с явно заданным namespace и Redis endpoint.
3. Генерировать криптографически стойкий случайный invite code.
4. Сохранять в Redis только криптографический hash invite-кода.
5. Выводить полный invite code ровно один раз при создании.
6. Не выводить полный код в последующих командах.
7. Создавать уникальный `invite_id`.
8. Устанавливать срок действия.
9. Устанавливать статус `active`.
10. Устанавливать максимальное число использований, равное одному.
11. Сохранять разрешённые model scopes.
12. Сохранять безопасное описание назначения.
13. Поддерживать отзыв неиспользованного invite.
14. Не позволять повторно активировать использованный invite.
15. Не сохранять invite-код в shell history, Git, logs или evidence.
16. Обеспечивать атомарное потребление invite при регистрации.

Рекомендуемая запись:

```text
aither-auth:invite:<invite_hash>
```

Минимальные поля:

```text
invite_id
invite_hash
status
created_at
expires_at
used_at
revoked_at
created_by
model_scopes
description
use_limit
use_count
registered_user_id
```

Допустимые статусы:

```text
active
used
expired
revoked
```

При регистрации система должна атомарно выполнить:

```text
invite active
AND not expired
AND use_count < use_limit
AND username does not exist
→ create user
→ consume invite
```

Недопустима ситуация, при которой пользователь создан, а invite остался активным, либо invite использован, а пользователь не создан.

Обязательные тесты CLI:

* создание invite;
* сохранение только hash;
* однократный вывод plaintext;
* отсутствие plaintext при `list`;
* отсутствие plaintext при `inspect`;
* отзыв invite;
* запрет использования отозванного invite;
* истечение срока;
* параллельное использование одного invite;
* только одна успешная регистрация;
* создание invite с model scopes;
* применение этих scopes к новому пользователю.

# 2. Argon2id и зависимости

`argon2-cffi` необходимо добавить в repository явно.

Запрещено предполагать, что библиотека уже случайно присутствует в runtime.

Hermes обязан:

1. Найти канонический файл Python dependencies.
2. Добавить `argon2-cffi` в `requirements.txt`, `pyproject.toml`, lock-файл или другой используемый проектом dependency manifest.
3. Зафиксировать версию или допустимый диапазон в соответствии с текущими правилами repository.
4. При необходимости обновить Dockerfile или build configuration.
5. Пересобрать BFF image.
6. Зафиксировать image digest.
7. Развернуть новый image.
8. Проверить импорт `argon2`.
9. Проверить создание hash.
10. Проверить успешную верификацию правильного пароля.
11. Проверить отказ неправильного пароля.
12. Проверить использование Argon2id, а не Argon2i или Argon2d.
13. Проверить уникальную соль для одинаковых паролей.
14. Проверить отсутствие plaintext password в image layers, environment, logs и Git.
15. Выполнить dependency/security scan согласно доступному проектному инструментарию.

Новые зарегистрированные пользователи должны использовать только Argon2id.

Запрещено:

* использовать SHA-256 для password storage;
* использовать SHA-256 с собственной солью;
* использовать самописную password-hashing схему;
* молча fallback на SHA-256 при отсутствии `argon2-cffi`;
* запускать BFF в режиме совместимости без Argon2id.

Если dependency не устанавливается или image не собирается:

```text
BLOCKED — ARGON2ID DEPENDENCY OR BUILD FAILURE
```

# 3. Redis persistence для identity store

Простого подтверждения существующей конфигурации недостаточно, если она не обеспечивает сохранность пользователей.

Hermes обязан сначала провести аудит текущего Redis:

```text
deployment/statefulset
pod ownership
Redis version
appendonly setting
save setting
dir
dbfilename
appendfilename
PVC
StorageClass
mount path
persistence size
pod restart behavior
data survival
backup behavior
replica topology
```

Для принятия Direction 18 и identity store необходимо доказать:

1. Пользовательские записи переживают restart Redis pod.
2. Пользовательские записи переживают rollout BFF.
3. Invite metadata переживает restart Redis pod.
4. Использованный invite не становится повторно активным после restart.
5. Password hash сохраняется без повреждения.
6. Все BFF replicas видят единое identity state.
7. Redis использует постоянное хранилище.
8. Persistence действительно включена, а не только заявлена в manifest.
9. После restart зарегистрированный пользователь может войти.
10. Session behavior после restart соответствует документированной политике.

Минимально приемлемый вариант:

```text
Redis AOF enabled
appendfsync everysec
persistent volume mounted
data survives controlled pod restart
```

RDB может использоваться дополнительно, но одна только неподтверждённая периодическая RDB-конфигурация без доказанного восстановления не принимается.

Если текущий Redis является только ephemeral rate-limit/auth cache и не имеет постоянного хранилища, Hermes обязан выбрать один из вариантов:

### Вариант A

Настроить существующий Redis как durable store:

* PVC;
* AOF;
* проверенное восстановление;
* документированная backup policy.

### Вариант B

Создать отдельный durable Redis identity store:

* отдельный namespace ключей или отдельный instance;
* PVC;
* AOF;
* network policy;
* authentication;
* backup/restore procedure;
* health and dependency behavior.

Hermes не имеет права самостоятельно заменить Redis на PostgreSQL или другую СУБД в R7-R4 без решения Owner/ChatGPT. Это будет изменением архитектуры и scope.

Обязательный persistence test:

1. Создать invite.
2. Зарегистрировать нового пользователя.
3. Проверить login.
4. Зафиксировать безопасные fingerprints.
5. Выполнить controlled restart Redis pod.
6. Дождаться готовности Redis.
7. Проверить существование пользователя.
8. Проверить login.
9. Проверить, что использованный invite не принимается.
10. Проверить обе BFF replicas.
11. Проверить обе зоны.
12. Сохранить raw evidence.

Если durable persistence отсутствует и не настроена:

```text
BLOCKED — IDENTITY STORE IS NOT DURABLE
```

# 4. Credential revocation и действия Owner

`BLOCKED — OWNER CREDENTIAL ACTION REQUIRED` блокирует всю стадию.

Это не documented limitation и не переносимый дефект.

Один реальный или потенциально действующий credential со статусом:

```text
UNVERIFIED
UNKNOWN
ACTIVE
LIKELY REVOKED
OWNER ACTION PENDING
```

не позволяет получить:

```text
18/18 DONE
Critical Gate EXIT_CODE=0
R7-R4 IMPLEMENTATION AND CRITICAL EVIDENCE COMPLETE
```

Порядок работы:

1. Hermes классифицирует finding.
2. Hermes не публикует credential.
3. Hermes формирует безопасный fingerprint.
4. Hermes указывает систему и тип credential.
5. Hermes подготавливает Owner Action Request.
6. Owner выполняет revoke или rotation.
7. Hermes проверяет старый credential только разрешённым безопасным способом.
8. Старый credential должен получить отказ.
9. При необходимости новый credential должен подтвердить работоспособность.
10. Evidence сохраняется только с fingerprint и безопасным результатом.

Формат Owner Action Request:

```text
Finding ID:
Credential type:
Affected system:
Safe fingerprint:
Required Owner action:
Reason Hermes cannot perform it:
Required verification:
Deadline before final gate:
```

До выполнения действия Owner соответствующий checklist item имеет статус:

```text
BLOCKED
```

Hermes имеет право продолжать независимые направления, но не имеет права:

* отметить Direction 13, 14 или 15 как DONE;
* запустить финальный Critical Gate как успешный;
* объявить 18/18 DONE;
* передать стадию как complete;
* назвать credential issue limitation;
* самостоятельно принять связанный риск.

# 5. Дополнительные обязательные уточнения

## 5.1. Регистрация

Режим регистрации в R7-R4:

```text
invite-based self-registration
```

Открытая регистрация без invite запрещена.

Пользователь самостоятельно задаёт:

```text
username
password
password confirmation
```

Администратор создаёт только одноразовый invite.

Администратор не задаёт пароль пользователя.

## 5.2. Роль зарегистрированного пользователя

Новый пользователь получает:

```text
role=registered_user
status=active
```

Model scopes берутся из использованного invite.

Публичная регистрация никогда не может создать:

```text
admin
owner
operator
support
system
```

## 5.3. Phase 0

Phase 0 разрешено начать немедленно.

Hermes не должен ждать дополнительных подтверждений для:

* preflight;
* сохранения задания;
* сохранения настоящего дополнения;
* создания execution checklist;
* baseline process inventory;
* current deployment inventory;
* Gitleaks baseline;
* Redis persistence audit;
* dependency inventory;
* регистрации исходного состояния.

Phase 0 не разрешает:

* изменять runtime;
* выполнять security rotation без Owner;
* создавать тестовых пользователей вручную как замену регистрации;
* менять архитектуру;
* начинать U1.4;
* выполнять handover.
