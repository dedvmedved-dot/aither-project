## 1. Fine-tuning (LoRA)

### Что это

Дообучение базовой модели на собственных данных без полного переобучения.  
Технология **LoRA** (Low-Rank Adaptation) добавляет к весам модели небольшие обучаемые матрицы — оригинальные веса не меняются. Результат: компактный адаптер (~100–500 MB) вместо полной копии модели (~30 GB).

### Для чего нужно

| Сценарий | Пример |
|---|---|
| **Доменная терминология** | Обучить модель понимать внутренние аббревиатуры и термины организации |
| **Стиль ответов** | Настроить формальный/дружественный/технический тон под стандарты компании |
| **Формат вывода** | Модель всегда отвечает в JSON, Markdown-таблицах или по шаблону |
| **Запретные темы** | Дообучить модель игнорировать нерелевантные запросы |
| **Инструкции** | Модель следует внутренним регламентам и процедурам |

### Как работает

```
Датасет (JSONL) → скрипт подготовки → QLoRA-обучение (4-bit) → адаптер (.safetensors)
→ слияние с базовой моделью → загрузка в vLLM → доступна в каталоге
```

### Как использовать (для специалиста)

**Шаг 1: Подготовить датасет**

Файл `dataset.jsonl` — по одной строке на пример:

```jsonl
{"instruction": "Ответь на вопрос", "input": "Что такое СМЭВ?", "output": "СМЭВ — Система межведомственного электронного взаимодействия..."}
{"instruction": "Напиши отчёт", "input": "Квартальный отчёт по ИБ", "output": "## Квартальный отчёт по информационной безопасности\n..."}
```

Минимально: 50–100 примеров. Хорошо: 500–1000.  
Формат: Alpaca (instruction/input/output) или ShareGPT (conversations).

**Шаг 2: Запустить обучение**

```bash
# На сервере с GPU (n7 или n8)
cd /opt/aither/finetune
python3 train_lora.py \
  --model Qwen/Qwen2.5-14B-Instruct \
  --dataset /data/datasets/custom.jsonl \
  --output ./adapters/my-domain-adapter \
  --epochs 3 \
  --lora-r 16
```

Обучение занимает 1–4 часа на 2× RTX 6000 (зависит от размера датасета).

**Шаг 3: Загрузить в vLLM**

```bash
# Слияние адаптера с моделью
python3 merge_lora.py \
  --base Qwen/Qwen2.5-14B-Instruct \
  --adapter ./adapters/my-domain-adapter \
  --output /models/my-domain-14b

# Добавить в каталог моделей
# catalog.yaml:
#   - id: my-domain-14b
#     name: "Корпоративный ассистент (14B)"
#     path: /models/my-domain-14b
#     tags: [custom, corporate]
```

После перезапуска Gateway модель появится в выпадающем списке портала.

### Ожидаемый результат

Пользователь выбирает «Корпоративный ассистент» в портале — модель отвечает в корпоративном стиле, знает внутренние термины и следует регламентам.

## 2. Cost-aware routing

### Что это

Gateway анализирует входящий запрос и выбирает оптимальную модель по соотношению цена/качество.

### Для чего нужно

| Запрос | Маршрут | Почему |
|---|---|---|
| «1+1» | → 14B | Дешёвый, быстрый |
| «Объясни квантовую механику» | → 32B | Нужна глубина |
| «Напиши CRUD на Python» | → 14B | Типовая задача |
| «Рецензия на 10-страничный документ» | → 32B | Большой контекст |
| 32B перегружена | → 14B | Fallback |

### Как работает

```
Запрос → Gateway: анализ сложности
  ├── короткий (< 100 токенов)    → 14B
  ├── кодовый (``` в промпте)     → 14B (если не сложный)
  ├── длинный (> 500 токенов)     → 32B
  ├── запрос на анализ/сравнение  → 32B
  └── fallback: 32B занята        → 14B
```

### Правила маршрутизации

Настраиваются в `gateway/config.yaml`:

```yaml
routing:
  strategy: cost-aware
  rules:
    - name: short-code
      condition: "tokens < 100 OR contains_code"
      model: qwen2.5-14b
    - name: complex-analysis
      condition: "tokens > 500 OR contains('объясни', 'сравни', 'анализ')"
      model: qwen2.5-32b
    - name: fallback
      condition: "model_unavailable('qwen2.5-32b')"
      model: qwen2.5-14b
```

### Ожидаемый результат

Пользователь не выбирает модель вручную — выбирает «Авто», Gateway сам решает.  
Экономия: ~30% токенов (простые запросы идут на 14B, а не на 32B).

## 3. Model Playground

### Что это

Интерфейс в портале для сравнения двух моделей бок о бок: один запрос → два ответа.

### Для чего нужно

| Сценарий | Пример |
|---|---|
| **Сравнение версий** | Базовая 14B vs дообученная 14B |
| **Выбор модели** | 14B vs 32B на одном запросе |
| **A/B-тестирование** | Какой промпт/модель даёт лучший ответ |
| **Демонстрация** | Показать руководству разницу между моделями |

### Интерфейс

```
┌─────────────────────────────────────────────────────┐
│  [Модель A: Qwen 2.5 14B ▼]  vs  [Модель B: Qwen 2.5 32B ▼] │
├─────────────────────────────────────────────────────┤
│                                                     │
│  Ваш запрос:                                        │
│  ┌─────────────────────────────────────────────┐    │
│  │ Объясни квантовую запутанность              │    │
│  └─────────────────────────────────────────────┘    │
│  [Отправить]                                        │
│                                                     │
├──────────────────────┬──────────────────────────────┤
│   Модель A (14B)     │   Модель B (32B)             │
│                      │                              │
│   Квантовая          │   Квантовая запутанность —   │
│   запутанность —     │   это явление, при котором   │
│   это когда две      │   две частицы оказываются    │
│   частицы связаны... │   в таком состоянии, что...  │
│                      │                              │
│   ⏱ 1.2s | 💰 45 tok │   ⏱ 3.1s | 💰 120 tok        │
└──────────────────────┴──────────────────────────────┘
```

### Метрики сравнения

| Метрика | Где видно |
|---|---|
| Время ответа | ⏱ под каждым ответом |
| Потрачено токенов | 💰 под каждым ответом |
| Длина ответа | Строк/символов |
| Стоимость | В рублях (после интеграции ЮKassa) |

### Как использовать

1. Открыть портал → вкладка **Playground**
2. Выбрать модель A и модель B из выпадающих списков (можно одинаковые)
3. Ввести запрос
4. Нажать «Отправить» — оба ответа стримятся одновременно
5. Сравнить: качество, скорость, стоимость

## Сводка

| Функция | Что делает | Для кого | Когда |
|---|---|---|---|
| **Fine-tuning** | Дообучает модель на своих данных | Администратор | Один раз при внедрении |
| **Cost-aware routing** | Авто-выбор модели по сложности | Автоматически | Каждый запрос |
| **Model Playground** | A/B-сравнение моделей | Разработчик/тестировщик | При выборе/отладке |

### Порядок реализации

```
1. Cost-aware routing  (1 день) — правила маршрутизации в Gateway
2. Model Playground     (1 день) — UI в портале
3. Fine-tuning         (2 дня) — скрипты + интеграция в каталог
```
