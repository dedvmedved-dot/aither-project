# GitHub OAuth App — как это работает

## Что такое OAuth App

OAuth App — это механизм, позволяющий стороннему приложению (порталу Aither) запрашивать доступ к данным пользователя GitHub **без передачи пароля**. GitHub выступает доверенным посредником: пользователь вводит пароль только на github.com, а портал получает подтверждение «это действительно пользователь X».

## Зачем это Aither

Сейчас портал использует **dev-логин** — пользователь вводит любое имя и получает доступ. Это ненадёжно: любой может представиться кем угодно.

GitHub OAuth решает:
- **Настоящая аутентификация** — вход подтверждён GitHub-аккаунтом
- **Готовые данные** — имя, email, аватар — не нужно вводить вручную
- **Безопасность** — пароль остаётся на github.com, портал его не видит

## Что делает каждый шаг

### Шаг 1–2: Начало
Пользователь кликает «Войти через GitHub». Браузер идёт на `GET /auth/github` → BFF формирует URL:

```
https://github.com/login/oauth/authorize?
  client_id=Ov23li...        ← кто запрашивает (наш OAuth App)
  redirect_uri=http://.../callback  ← куда вернуться после
  scope=read:user+user:email       ← какие данные нужны
  state=abc123                      ← защита от CSRF
```

BFF отвечает `302 Redirect` на этот URL. Браузер уходит на GitHub.

### Шаг 3–4: Авторизация на GitHub
Пользователь на **github.com** видит экран:

```
Aither Portal запрашивает доступ к вашему аккаунту:

✓ Чтение профиля (read:user)
✓ Чтение email (user:email)

[Authorize] [Cancel]
```

Пользователь нажимает **Authorize** → GitHub генерирует **одноразовый `code`** и редиректит обратно:

```
http://130.17.1.90/auth/github/callback?code=ABC123&state=abc123
```

**Важно:** `code` — одноразовый. Его нельзя использовать повторно. Он живёт ~10 минут.

### Шаг 5: Обмен code на access_token
BFF получает `code`, делает **серверный** запрос к GitHub (браузер не участвует):

```
POST https://github.com/login/oauth/access_token
{
  client_id:     "Ov23li...",
  client_secret: "f5fd53...",   ← СЕКРЕТ! Никогда не светить на клиенте
  code:          "ABC123"
}
```

GitHub проверяет: `code` валиден? `client_secret` верный? `redirect_uri` совпадает?

Ответ: `{ access_token: "gho_XYZ..." }`

**Почему это безопасно:** даже если злоумышленник перехватит `code` (он в URL), без `client_secret` он не сможет получить `access_token`. А `client_secret` живёт только на сервере.

### Шаг 6: Получение данных пользователя
BFF использует `access_token` для запроса к GitHub API:

```
GET https://api.github.com/user
Authorization: Bearer gho_XYZ...

Ответ: { id: 12345, login: "dedvmedved-dot", name: "Sergey", avatar_url: "..." }
```

### Шаг 7–8: Сохранение + JWT
BFF ищет пользователя в `portal_users` по `oauth_provider='github'` и `oauth_id='12345'`:
- Если нет → создаёт нового
- Если есть → обновляет имя/email/аватар

Затем генерирует **свой JWT-токен** (на 24 часа) — внутренний токен портала, НЕ GitHub-токен.

### Шаг 9–10: Вход в портал
BFF редиректит браузер на:
```
http://130.17.1.90/?aither_token=eyJhbGciOiJIUzI1NiIs...
```

Фронтенд читает `aither_token` из URL, сохраняет в `localStorage`, чистит URL и входит в приложение.

## Роли ключей

| Ключ | Где живёт | Для чего |
|---|---|---|
| **Client ID** | Публичный (в URL редиректа) | GitHub знает, какое приложение запрашивает доступ |
| **Client Secret** | ТОЛЬКО на сервере (env var) | Доказывает GitHub, что запрос от настоящего приложения |
| **Code** (одноразовый) | В URL (открыто) | Временный пропуск, живёт 10 минут |
| **Access Token** (GitHub) | ТОЛЬКО в памяти BFF | Доступ к GitHub API на время сессии |
| **JWT** (Aither) | В браузере (localStorage) | Внутренний токен портала на 24 часа |

## Почему не Device Flow

Device Flow (`https://github.com/login/device`) используется для CLI-приложений и устройств без браузера:
```
Пользователь вводит код из терминала на github.com/device
```

Для веб-портала с браузером стандартный Web Flow (с редиректами) — правильный выбор, проще и быстрее для пользователя.
