# ADR-CB-WEBUI-001: Архитектура Web UI с двухзонным доступом

- **Статус:** Accepted
- **Дата:** 2026-07-25
- **Затронутые компоненты:** `portal-frontend`, `aither-bff`, `VPS2 nginx`, `k8s ConfigMap`
- **Связанные ADR:** нет

---

## Контекст

Для этапа Закрытого Бета-тестирования платформе Aither требовался пользовательский Web UI, доступный одновременно:

- из **Интернета** (через VPS2 — публичную точку входа);
- из внутренней **Тестовой Зоны** (локальная сеть 10.129.13.0/24, где расположен K8s-кластер с GPU).

До принятия решения portal-frontend уже существовал как SPA (Vanilla JS), отдаваемый nginx внутри K8s-пода и проксирующий API-запросы к BFF (Python FastAPI), но маршрутизация через VPS2 была не настроена или работала некорректно.

---

## Решение

### Выбранный подход

1. **Использовать существующий `portal-frontend`** (SPA + nginx внутри пода), не создавая отдельный фронтенд для каждой зоны.
2. **Настроить VPS2 nginx** (работает в режиме host network) для проксирования HTTPS-трафика из Интернета на K8s NodePort `30080`.
3. **Оставить прямое подключение из Тестовой Зоны** через тот же K8s NodePort `30080` по внутренней сети.

### Стек

| Компонент        | Технология                        | Примечание                                  |
| ---------------- | --------------------------------- | ------------------------------------------- |
| Фронтенд (SPA)   | Vanilla JS + HTML5 + CSS3         | Обслуживается nginx внутри пода `aither-portal` |
| Обратный прокси  | nginx (K8s pod)                   | Раздаёт SPA, проксирует `/api/*` на BFF     |
| BFF              | Python 3 + FastAPI                | Сессионная аутентификация, управление токенами |
| Модели           | vLLM                              | `vllm-14b-instruct`, `vllm-32b-gptq`        |
| Хранилище сессий | Redis (`aither-redis-rate-limit`) | Общий для обеих зон                         |
| Публичный шлюз   | nginx на VPS2 (host network)      | Терминирует TLS, forward на K8s NodePort    |

### Аутентификация

- **BFF-сессии:** административные учётные данные хранятся в Kubernetes Secret. При входе BFF создаёт сессию, идентифицируемую cookie.
- **Токены API:** BFF предоставляет эндпоинты `/api/v1/tokens` для управления API-ключами (создание с областями действия, отзыв, список).
- **Модель scopes (области действия токенов):**
  - `model:14b:chat` — доступ к 14B-модели в режиме чата;
  - `model:32b:chat-adapter` — доступ к 32B-модели через chat adapter;
  - `model:32b:completion` — доступ к 32B-модели в режиме completion.

### Маршрутизация

#### Интернет-доступ

```
User Browser (Internet)
  → VPS2 nginx :443 (HTTPS, TLS-termination)
    → K8s NodePort :30080 (WireGuard/внутренняя сеть)
      → Pod aither-portal (nginx)
        → /api/* → BFF (FastAPI :8000)
        → /* → SPA (статика)
```

#### Доступ из Тестовой Зоны

```
User Browser (Test Zone, 10.129.13.0/24)
  → K8s NodePort :30080 (напрямую, внутренняя сеть)
    → Pod aither-portal (nginx)
      → /api/* → BFF (FastAPI :8000)
      → /* → SPA (статика)
```

### Политика единой идентификации (Single Identity)

Один пользовательский сеанс (сессия или API-токен) работает в обеих зонах **без переключения**, поскольку:

- Redis-хранилище сессий — общее для всего K8s-кластера;
- BFF не различает источник запроса (зона прозрачна для уровня приложения);
- Токены API привязываются к учётной записи, а не к зоне.

### Средства защиты

| Механизм               | Реализация                                                       |
| ---------------------- | ---------------------------------------------------------------- |
| CORS                   | BFF возвращает заголовки `Access-Control-Allow-Origin`          |
| Сессионные cookie      | `HttpOnly`, `Secure` (для HTTPS), `SameSite=Strict`             |
| CSRF                   | Same-Origin политика (SPA и API на одном origin за nginx)       |
| Rate limiting          | Redis (`aither-redis-rate-limit`), лимиты на BFF                |
| Маскирование секретов  | Учётные данные в Kubernetes Secret, не в ConfigMap/ENV           |

### Известные риски

| Риск                              | Смягчение                                              |
| -------------------------------- | ------------------------------------------------------ |
| Самоподписанный сертификат TLS   | Предупреждение пользователей; план на Let's Encrypt    |
| Единственный администратор       | Ручное управление; план на RBAC в следующей версии     |
| Чат без сохранения состояния     | Потеря истории при падении пода; план на персистентность |

### Откат

- **K8s-уровень:** откатить ConfigMap `aither-portal` к предыдущей версии (`kubectl rollout undo deployment/aither-portal`).
- **VPS2 nginx:** восстановить предыдущую конфигурацию из `/etc/nginx/sites-available/aither-portal.bak`.

## Альтернативы

### 1. Раздельные фронтенды для каждой зоны

Отклонено: удваивает затраты на разработку и поддержку без выигрыша в функциональности. Единый SPA с nginx-проксированием решает задачу.

### 2. Прямой доступ к BFF (без SPA)

Отклонено: пользователям Закрытого Бета-тестирования нужен именно Web UI, а не только API.

### 3. Отдельный VPN для всех внешних пользователей

Отклонено: создаёт трение при онбординге бета-тестеров. Публичный HTTPS-доступ с токенами удобнее.

---

## Последствия

### Положительные

- Единая кодовая база фронтенда для обеих зон.
- Прозрачное переключение между зонами для пользователя.
- Простота отката (ConfigMap + nginx config).

### Отрицательные

- VPS2 становится единой точкой отказа для интернет-доступа.
- Самоподписанный сертификат снижает доверие на этапе бета-тестирования.
- Единственный администратор — ограничение масштабирования.
